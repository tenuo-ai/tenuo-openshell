# Issuing warrants in production

This guide covers the keys that sign Tenuo material and where each should
live, and how a platform that runs agents for many users can issue one
warrant per request
([#17](https://github.com/tenuo-ai/tenuo-openshell/issues/17)). Read it with
[Architecture](architecture.md#holder-key-custody), the
[threat model](threat-model.md), and the [operations runbook](operations.md).

## Recommended: Tenuo Cloud

For a managed setup, use [Tenuo Cloud](https://tenuo.ai) as the issuer. It
runs the parts of this guide that are hardest to operate yourself:

- **Issuer keys in a KMS.** Each tenant's root signing key is created and
  held in Google Cloud KMS (`EC_SIGN_ED25519`), and never leaves it. Cloud
  handles root key rotation.
- **Per-request issuance.** Triggers mint a short-lived warrant to a
  registered agent's public key, with the capabilities that trigger
  allows. Every issuance is recorded with its resolved constraints and the
  event that caused it.
- **Approvals with bound identities.** Approvers approve in the dashboard,
  Slack, Telegram, email, or a webhook. Each decision is signed and bound to
  the approver's identity.
- **Revocation.** Cloud publishes each tenant's signed revocation list in
  the Tenuo core format the middleware verifies.

Cloud's clients are part of Tenuo itself:

- **Revocation sync and receipts:** core's control-plane client, configured
  by `TENUO_CONTROL_PLANE_URL` and `TENUO_API_KEY`, or a connect token.
- **Warrant fetch:** the `tenuo-cloud` SDK fires a trigger and binds the
  warrant to the local holder key.
- **Approvals:** the SDKs submit an approval request and wait for the signed
  decision.

Authorization never waits on Cloud. The middleware verifies warrants offline
against the roots in its policy. To use Cloud as the issuer:

1. Put the tenant's root public key (`GET /v1/keys`) in each sandbox's
   `trusted_roots`.
2. Register the sandbox's holder public key, from
   `tenuo-openshell-agent keygen`, as an agent.
3. Fire the trigger, and install the warrant in the sandbox with
   `tenuo-openshell-agent install-warrant`.

The middleware and the sandbox agent do not run these clients yet:

- [#20](https://github.com/tenuo-ai/tenuo-openshell/issues/20) tracks
  revocation sync and receipt export in the middleware.
- [#19](https://github.com/tenuo-ai/tenuo-openshell/issues/19) tracks
  approval requests from the sandbox agent.

Until those land, copy Cloud's signed revocation list into the policy's
`revocation` block, and approve held calls with `tenuo-openshell approve`.

The rest of this guide is for running issuance yourself: air-gapped
deployments, or teams that must hold every key in their own infrastructure.

## Roles and keys

Every Tenuo key is Ed25519. Give each role its own key. Reusing one key for
two roles adds the blast radius of both.

| Role | Signs | Who trusts it | Where the key lives |
| --- | --- | --- | --- |
| Issuer | Root warrants, and the signed revocation lists (SRLs) for sandboxes that trust it | The middleware, through each sandbox's `trusted_roots` | An issuance service or host outside every sandbox and outside the middleware. One key per environment, and per tenant where tenants have separate sandboxes. |
| Orchestrator (attenuator) | Child warrants, by attenuating a parent warrant it holds | The chain: the parent names this key as holder | The orchestrator's host, outside the sandbox |
| Approver | Approvals for tools that require them | Warrants that list it in `required_approvers` | With the human or approval service that reviews requests |
| Holder | A proof of possession for each tool call | The leaf warrant names it | Inside the sandbox, generated by `tenuo-openshell-agent keygen` |
| Receipt signer | Authorization and result receipts | Whoever verifies receipts, through the `.pub` file | The middleware (`--receipt-key`), mounted from a Secret |
| Policy signer | `policy.json.sig` over the SHA-256 of the policy | The middleware, through `--policy-signing-key` | Wherever policy changes are reviewed and released, never on the middleware |

What an attacker gets with each key, and how to replace it:

| Role | Blast radius | Rotation |
| --- | --- | --- |
| Issuer | Any tool and any arguments, in every sandbox whose `trusted_roots` lists the key. Each forged warrant is limited by `max_warrant_lifetime_secs` in sandboxes without revocation, but the attacker can keep minting new ones. The key also signs SRLs, so it can publish a higher-version list that drops revoked ids. | Add the new public key to `trusted_roots` in a higher policy version. Switch issuance to the new key. Wait for the longest outstanding warrant to expire, then remove the old key in another version. |
| Orchestrator | Anything inside its parent warrant: those tools and constraints, until the parent expires. It cannot widen the parent. | Issue a new parent warrant to a new key. Revoke the old parent's id, which ends every child signed under it in sandboxes with revocation. |
| Approver | Approves any pending request in warrants that list it. It cannot create authority, and each approval is single-use. | List the new key in newly issued warrants. Existing warrants accept the old key until they expire, so short lifetimes make this quick. |
| Holder | One task's warrant, until it expires or is revoked. | Per task: `provision` again. The key and warrant are replaced together. |
| Receipt signer | Forged receipts. It grants no authority. | Mount a new immutable Secret and restart. Keep the old `.pub` file to verify old logs. |
| Policy signer | Equivalent to every issuer at once: it chooses the trusted roots for every sandbox. | Sign the current policy with the new key, then roll the middleware with the new `--policy-signing-key`. |

The OpenShell extension JWT key and the middleware TLS key authenticate
transport, not authority. See [Deployment](deployment.md) and
[Key compromise](operations.md#key-compromise).

## Issuer custody

### What the tooling does today

`tenuo-openshell warrant issue`, `provision`, and `approve` read the issuer,
parent, or approver key from a file, either 32 raw bytes or 64 hex
characters. Tenuo core 0.3.2 has no way to mint a root warrant with a key it
cannot read. The next section has the details.

A file key is a reasonable production design when the file is in the right
place:

1. **Put issuance in its own service.** The orchestrator asks it for warrants
   and never holds the issuer key. Then code execution in the orchestrator, or
   in an agent the orchestrator runs, can only request warrants the service is
   willing to grant. [Per-request issuance](#per-request-issuance-for-multi-user-platforms)
   describes this service.
2. **Deliver the key from a secret manager at start.** Use a Kubernetes Secret
   volume with encryption at rest backed by your KMS, the Vault Agent
   injector, or the Secrets Store CSI driver. Mount it read-only, mode `0400`,
   owned by the service user, on `tmpfs`. Do not pass it in an environment
   variable: those leak through `/proc`, crash dumps, and child processes.
   Never bake it into an image or commit it.
3. **Keep it out of everything else.** It belongs in no sandbox, not in the
   middleware pod, not on the operator laptops that run `approve`, and not in
   CI logs.
4. **Restrict who can reach the service.** Accept only the orchestrator's
   workload identity, over mTLS. Apply NetworkPolicy so nothing else can reach
   it.
5. **Bound what one key can do.** Use one issuer per environment, and per
   tenant if tenants have separate sandboxes, so `trusted_roots` contains the
   damage. Keep `max_warrant_lifetime_secs` short. The middleware applies it
   to every warrant in a chain when the sandbox has no revocation list.
6. **Audit every mint.** Write the warrant id, principal, task, holder, and
   expiry to an append-only store. A mint you cannot match to a request is
   evidence of compromise.

**Offline root, online parent.** To keep the root key offline, mint a parent
warrant from an offline host to a key the issuance service holds, and have
the service attenuate from it with `--parent-key` and `--parent-warrant`. The
online key's blast radius is then the parent warrant, not every tool. Revoking
the parent's id ends everything issued under it. A chain is checked against
`max_warrant_lifetime_secs` at every link, so a parent that lives longer than
that requires the sandbox to have a `revocation` entry.

**Per-environment keys from one seed.** If you need deterministic recovery,
you can derive each environment's issuer key from an offline master seed with
HKDF-SHA256, using the environment name as `info`. Compromising one derived
key does not reveal the master or the other keys, but losing the master loses
them all. Prefer independently generated keys, each backed up on its own,
unless deterministic recovery is a requirement.

### KMS and HSM signing

Tenuo verifies standard RFC 8032 Ed25519 (PureEdDSA) signatures over a byte
string Tenuo builds itself. A signer that holds the key elsewhere has to sign
those exact bytes, unhashed. Ed25519ph (prehash) signatures do not verify.

Tenuo core 0.3.2 supports this for only some operations:

| Operation | API in `tenuo` 0.3.2 | Key held elsewhere? |
| --- | --- | --- |
| Mint a root warrant | `WarrantBuilder::build(self, &SigningKey)`. `IssuanceBuilder::build` and `OwnedIssuanceBuilder::build` also take `&SigningKey`. The payload's `issuer` comes from `signing_key.public_key()`. | No |
| Attenuate (Rust) | `AttenuationBuilder::prepare() -> PreparedDelegation`, then `final_signing_bytes()` and `finalize(Signature)`. `finalize` verifies the signature against the parent holder. `build(&SigningKey)` is sugar over these. | **Yes** |
| Attenuate (SDK) | `HolderSigner::sign_delegation(&DelegationSigningRequest)`, used by `PresentedAuthority::delegate_to` | **Yes**, synchronously |
| Attenuate (Python, TypeScript) | `Warrant.attenuate(signing_key=...)` and `OwnedAttenuationBuilder::build(&SigningKey)` | No |
| Proof of possession | `HolderSigner::sign_pop`, `AsyncHolderSigner::sign_pop` | Yes. Not needed here: the holder key belongs in the sandbox. |
| Approve | `SignedApproval::create(ApprovalPayload, &SigningKey)`, `sdk::approve_request(.., &SigningKey, ..)`, `LocalApprovalSigner::new(SigningKey, ..)`. The approval preimage builder is private. | No |
| Signed revocation list | `SrlBuilder::build(self, &SigningKey)`, `SignedRevocationList::empty(&SigningKey)`. The fields are private. | No |
| Receipt | The `ReceiptSigner` trait in the SDK runtime. `Receipt::signing_preimage` and the `Receipt` fields are public. This repository's `ReceiptLog` still calls `Receipt::create(&ReceiptPayload, &SigningKey)`. | Yes |
| Python `SigningKey` | Built from bytes or a file, in process | n/a |

So with core 0.3.2:

- An orchestrator written in Rust can keep its parent-holder key in a KMS
  today, using `prepare` and `finalize`.
- Root issuance, approvals, and SRLs need a core change before a KMS or HSM
  can sign them. [docs/upstream/core-external-signer.md](upstream/core-external-signer.md)
  is the proposal.

Ed25519 support across key services, checked against vendor documentation on
2026-10-04:

| Service | Ed25519 | Identifiers | Pure Ed25519 over the raw message | Limits and notes |
| --- | --- | --- | --- | --- |
| AWS KMS | Yes (announced 2025-11) | Key spec `ECC_NIST_EDWARDS25519`, usage `SIGN_VERIFY`; algorithm `ED25519_SHA_512` | Yes, with `MessageType=RAW` | Message at most 4096 bytes. `ED25519_PH_SHA_512` is prehash and does not verify under Tenuo. `GetPublicKey` returns DER SubjectPublicKeyInfo. |
| Google Cloud KMS | Yes | `EC_SIGN_ED25519`, purpose `ASYMMETRIC_SIGN` | Yes. Send `data`, not `digest`. | **`SOFTWARE` protection level only.** Not available at `HSM`, `HSM_SINGLE_TENANT`, or `EXTERNAL`. |
| Azure Key Vault and Managed HSM | **No** | Key types are RSA, EC (P-256, P-256K, P-384, P-521), and oct | n/a | Use a PKCS#11 HSM or another provider. |
| HashiCorp Vault Transit | Yes | Key type `ed25519`; `POST /transit/sign/:name` | Yes. `prehashed` defaults to false, and `hash_algorithm` is ignored for ed25519. | Keys are in Vault's storage, not an HSM. |
| PKCS#11 HSMs | Yes, PKCS#11 3.0 and later | `CKK_EC_EDWARDS`, `CKM_EC_EDWARDS_KEY_PAIR_GEN`, `CKM_EDDSA` | Yes. Use `CKM_EDDSA` with no parameters. | Thales Luna 7 and 10 and Entrust nShield 13 document `CKM_EDDSA`. AWS CloudHSM uses a vendor mechanism, `CKM_CLOUDHSM_EDDSA`, only on `hsm2m.medium` in non-FIPS mode. SoftHSMv2 supports EdDSA for testing. |
| YubiHSM 2 | Yes | Algorithm `ed25519`, capability `sign-eddsa` | Yes | Message at most 2019 bytes. |

FIPS validation of Ed25519 differs by product and mode. Confirm it with your
vendor if it is a requirement.

The message limits matter for Tenuo. A warrant's signed bytes are a short
context string, a version byte, and the CBOR payload. A typical two-tool
warrant payload is about 400 bytes, but the protocol allows warrants up to
64 KiB. A KMS-backed signer must refuse a message over its limit rather than
fall back to prehash. The policy signature covers a fixed 57-byte message
(a context string and the SHA-256 of `policy.json`), so a KMS-held policy key
works at any policy size.

## Per-request issuance for multi-user platforms

OpenShell policy is fixed per sandbox. On a platform that runs agents for many
users, authority should depend on who asked and for what. Issue one warrant
per request, scoped to that user and task, to a holder key generated for that
task:

```text
user ──► platform ──► orchestrator
                        │ 1. keygen in the task's sandbox → holder public key
                        │ 2. POST /v1/warrants (orchestrator identity,
                        │    user's token, task, holder)
                        ▼
                   issuance service ── authenticates both, maps
                        │              (user, task) to capabilities,
                        │              mints a short-lived root,
                        │              audits the mint
                        ▼
                   orchestrator ── 3. install-warrant in the sandbox
```

### The issuance service

1. **Authenticate the caller and the user.** The caller is the orchestrator,
   identified by its workload identity over mTLS. The user arrives as a token
   the service verifies itself: an OIDC ID token or an OAuth token-exchange
   (RFC 8693) token whose audience is the issuance service. Never accept a
   user name the orchestrator merely asserts.
2. **Map to capabilities.** A grants policy maps each user, or group, and task
   to tools and argument constraints, in the same format as `--capabilities`.
   The warrant is that entry, or the intersection of the task template and
   the user's entitlements. Grant nothing for an unlisted pair. Arguments
   come from policy, never from the request.
3. **Mint short-lived.** Use a root warrant to the holder key the orchestrator
   supplied, with a lifetime of minutes and a cap the request cannot raise.
   Put the user in the warrant: `session_id` is signed, so every receipt's
   warrant chain names the principal. Alternatively, attenuate from a
   long-lived parent the service holds. See
   [Offline root, online parent](#what-the-tooling-does-today).
4. **Audit, then return.** Append the warrant id, principal, task, holder, and
   expiry, then return the encoded warrant. The receipts' `warrant_id` joins
   to this log.

### Delivery

The orchestrator already runs `provision`'s steps itself. It replaces the
issuer key with a call to the service:

```bash
holder="$(openshell sandbox exec --name "$sandbox" --no-tty -- tenuo-openshell-agent keygen)"
warrant="$(curl -sf --cert orchestrator.pem --key orchestrator-key.pem \
  -H "Authorization: Bearer $user_token" \
  -d "{\"holder\":\"$holder\",\"task\":\"triage\",\"ttl\":600}" \
  https://issuance.internal/v1/warrants | jq -r .warrant)"
openshell sandbox exec --name "$sandbox" --no-tty -- tenuo-openshell-agent install-warrant "$warrant"
```

The proxy re-reads the warrant file on every call, so a new warrant takes
effect without a restart. Re-issue before expiry for a long task. The agent's
`install-warrant` rejects a warrant for any key but its own.

### API sketch

```text
GET  /v1/issuer
  200 {"public_key": "<64 hex>"}            value for trusted_roots

POST /v1/warrants
  Authorization: Bearer <user token>        plus orchestrator mTLS
  {"holder": "<64 hex>", "task": "triage", "ttl": 600}
  201 {"warrant": "<base64 warrant stack>", "warrant_id": "tnu_wrt_…",
       "session_id": "alice/<request id>", "principal": "alice",
       "tools": ["read_logs"], "expires_at": 1767225600}
  400 malformed holder, task, or ttl; holder equal to the issuer
  401 unauthenticated
  403 no grant for this principal and task

POST /v1/revocations                         operators only
  {"warrant_id": "tnu_wrt_…"}
  202 the next SRL version includes it
```

[`examples/issuance/`](../examples/issuance/README.md) implements the first
two endpoints in under 300 lines of Python on the public `tenuo` 0.3.2
package. Its test issues the same task to two users, checks that each warrant
carries only that user's argument limits, and installs both with the real
agent. Revocation is not in the example: building an SRL also needs the
issuer key, and the policy carries it per sandbox (see
[Revocation](deployment.md#revocation)).

### Why this is safe

- **Short lifetime.** A stolen warrant, or a mistaken grant, lasts minutes.
  The middleware also refuses links that live longer than
  `max_warrant_lifetime_secs` in sandboxes without revocation.
- **Narrow capabilities.** The grant names tools and argument values, so a
  prompt-injected agent acting for Alice is limited to what Alice could
  request for that task.
- **Holder binding.** Every call needs a proof signed by the task's key, which
  never leaves the sandbox. A warrant intercepted on its way to the sandbox,
  or read from the audit log, is useless elsewhere.
- **Revocation.** Sandboxes with a signed revocation list stop a warrant, and
  everything delegated from it, as soon as the replicas hold the new list.
- **Attribution.** The issuance log maps each warrant id to a principal. Each
  receipt names the leaf warrant id and carries the signed chain, including
  `session_id`.

### Concurrency and isolation

The middleware selects trust by `sandbox_id`, and anything in a sandbox can
use its loopback proxies (threat model
[#20](threat-model.md#threats-and-mitigations)). Tasks in one sandbox are
therefore not isolated from each other:

- **Different users: one sandbox per user session.** Then a compromised task
  can reach only its own user's authority, and per-tenant issuer keys work
  through `trusted_roots`.
- **Concurrent tasks for one user in one sandbox:** run one proxy per task,
  each with its own `TENUO_HOLDER_KEY_FILE`, `TENUO_WARRANT_FILE`,
  `TENUO_APPROVALS_DIR`, and `--listen` port, as for
  [sub-agents](sandbox-agent.md#sub-agents). Each task gets its own
  attribution and its own expiry. It does not get a security boundary from
  the other tasks.

A sandbox created on demand also needs a policy entry before its first call.
The platform controller writes it, either through `tenuo-openshell policy add`
or a [policy provider](providers.md).

## Rotation and compromise

Routine rotation is in the [roles table](#roles-and-keys). For a suspected
issuer, orchestrator, or approver compromise:

1. Stop the issuance service, or block its network path, so no new warrants
   are minted with the key.
2. Remove the key from `trusted_roots` in a higher policy version. Every
   warrant chained to it then denies on the next poll, whatever its expiry.
   For an orchestrator or approver key, revoke the affected warrant ids
   instead, or wait out their short lifetimes.
3. Publish an SRL for warrants that stay trusted but must stop. A
   compromised issuer's own SRLs cannot be trusted, so its removal from
   `trusted_roots` is what ends its authority.
4. Bring a new key online. Add its public key in the same or a later policy
   version, then resume issuance.
5. Use the issuance audit log to list every warrant minted during the
   exposure. Compare it with receipts by `warrant_id` and `root_principal`. A
   receipt whose warrant id is not in the issuance log was minted by someone
   else.

Then follow [Key compromise](operations.md#key-compromise) for the receipt,
TLS, and gateway keys, and preserve evidence as it describes.
